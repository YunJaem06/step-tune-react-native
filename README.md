# 부동산 실거래 지도 · 단지 비교 앱

아파트 실거래가를 지도에서 탐색하고, 관심 있는 단지의 가격과 건물 정보를 같은 조건으로 비교하는 모바일 앱을 개발합니다. React Native 앱과 Kotlin/Spring Boot 서버를 직접 개발하며 학습하는 프로젝트입니다.

> 프로젝트 이름은 추후 변경 예정입니다. 현재 저장소·패키지 이름과 `StepTune RN` 표시 이름은 기존 값을 사용합니다. 이 문서는 2026-10-23에 정리한 개발 계획이며, 아래의 **현재 구현 상태**와 **도입 예정 기술**을 구분합니다.

## 첫 버전 범위

- **대상 데이터:** 한 시·군·구의 아파트 매매, 최근 3년 거래
- **개발 대상:** Android 우선, 이후 iOS 검증
- **핵심 흐름:** 지도 탐색 → 단지 상세 → 후보 2~3개 비교 → 관심 저장
- **주요 화면:** 지도, 단지 상세, 비교함, 관심 목록
- **접근 방식:** 지도·상세·비교는 비회원도 탐색하고, 계정에 관심 목록을 저장할 때 로그인

공공 실거래 데이터로 신고된 거래를 보여줍니다. 현재 판매 중인 매물이나 호가를 제공하는 서비스와는 데이터 성격이 다르므로, 화면에는 거래 가격·면적·계약 시점을 명시합니다.

### 핵심 기능

| 기능 | 첫 버전 동작 |
| --- | --- |
| 실거래 지도 | 단지별 가격 마커, 단지 묶음 표시, 지도 이동 후 해당 영역 검색 |
| 검색·필터 | 지역·단지명 검색, 거래가격·전용면적·건축연도·계약 기간 필터 |
| 단지 상세 | 기본정보, 면적별 거래, 계약일·가격·면적·층을 포함한 거래 목록 |
| 거래 그래프 | 면적대·기간별 거래 산점도, 거래 선택 시 상세 표시, 거래 건수 표시 |
| 단지 비교 | 최대 3개 후보에 같은 면적대·기간을 적용하고 가격·거래 건수·건물정보 비교 |
| 관심 목록 | 단지 저장·해제, 개인 메모, 계정별 저장 및 재조회 |

첫 버전 이후에는 신규 실거래 알림, 비교 결과 공유, 같은 거래가격대에서 면적·건축연도 조건을 바꿔보는 탐색 기능을 확장 후보로 둡니다.

## 서버 기술스택

서버 프로젝트는 아직 생성하지 않았습니다. 앱 저장소와 별도의 저장소로 구성하는 것을 권장하며, 다음 기술을 도입할 계획입니다.

| 구분 | 기술 | 용도 |
| --- | --- | --- |
| 언어·프레임워크 | Kotlin / Spring Boot 4.1.x | Kotlin 버전은 Spring Initializr 호환 조합으로 선택 |
| 실행·빌드 | JDK 21 / Gradle Kotlin DSL | 서버 실행·의존성·빌드 관리 |
| API | Spring MVC / REST | 지도·상세·거래·비교·관심 목록 API |
| DB | PostgreSQL / PostGIS | 거래 저장, 좌표 저장, 지도 범위 검색 및 공간 인덱스 |
| DB 접근 | Spring Data JPA / Hibernate Spatial / 필요한 집계 SQL | 일반 데이터 처리, 공간 조회, 가격·거래 건수 집계 |
| DB 변경 관리 | Flyway | 테이블·인덱스·PostGIS 설정의 변경 이력 관리 |
| 외부 데이터 연동 | Spring RestClient / XML 파싱 | 공공 실거래 데이터 수집 |
| 정기 수집 | Spring Scheduling / 수집 이력 테이블 | 재수집·재시도·중복 실행 방지 |
| 인증 | Spring Security / Google 인증 / Access·Refresh Token | 사용자 인증과 계정별 데이터 접근 제어 |
| API 문서 | springdoc-openapi / Swagger UI | 앱·서버 API 계약 확인 |
| 테스트 | JUnit / Testcontainers | 실제 PostgreSQL·PostGIS 기반 통합 검증 |
| 로컬 환경 | Docker Compose | DB 등 개발 환경 구성 |
| 빌드·배포 | Docker / GitHub Actions | 자동 검사와 배포 구성 |

초기 서버는 단일 Spring Boot 애플리케이션으로 구성하고, 단지·거래·수집·회원·관심 목록을 기능별 패키지로 나눕니다. 공공데이터를 수집하는 코드와 앱에 조회 결과를 제공하는 코드는 역할을 구분합니다.

첫 배포 후보는 Docker 서버와 관리형 PostgreSQL을 제공하는 Render입니다. PostGIS 지원, 실행 자원, 정기 수집이 동작할 운영 조건과 비용을 확인한 뒤 배포 환경을 결정합니다.

## 데이터 흐름과 처리 기준

**공공 API → 서버 수집·정제 → PostgreSQL/PostGIS → 서버 API → 모바일 앱**

앱은 서버가 정리한 데이터를 조회합니다. 공공 API 수집과 주소→좌표 변환은 서버에서 담당합니다.

| 원천 | 활용 계획 |
| --- | --- |
| 국토교통부 아파트 매매 실거래가 상세 자료 | 계약일·거래가격·면적·층 등 거래 데이터 |
| 건축HUB 건축물대장 | 단지·건물 기본정보 보강, 연결 가능한 항목부터 적용 |
| 주소→좌표 변환 API | 단지 위치를 지도 좌표로 연결, 제공자·이용 조건은 초기 검증에서 확정 |

데이터 품질과 화면 표시 기준은 다음과 같이 잡습니다.

- 공공 API의 원본 응답, 수집 범위, 수집 시각과 성공·실패 이력을 보관합니다.
- 원본 식별정보와 정정 규칙을 확인해 중복 수집을 방지합니다. 가격·계약일이 같다는 이유만으로 다른 거래를 합치지 않습니다.
- 주소·원천 식별정보를 확인해 단지를 연결합니다. 단지명만으로 합치지 않으며, 확인되지 않은 연결은 보류합니다.
- 정정·해제를 재수집에 반영합니다. 해제 거래는 내역에서 구분하고 가격 집계에서 제외합니다.
- 금액은 원 단위 정수로 표준화하고, 면적은 소수 정밀도를 유지한 ㎡ 단위로 저장합니다. 계약일과 수집·갱신 시각은 별도로 관리합니다.
- 지도·상세·비교는 동일한 면적대·기간·거래 포함 기준을 사용합니다.
- 최근 거래 가격에는 면적·계약일·층을 함께 표시하고, 집계 가격에는 집계 기간과 거래 건수를 함께 표시합니다.
- 거래 없음, 정보 없음, 수집 실패를 구분하고 마지막 갱신 시각을 제공합니다.
- API 키 등 인증정보는 README에 기록하지 않고 환경 설정으로 관리합니다.

## 개발 순서

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 0. 핵심 기술 검증 | 첫 지역 선정, 공공 API 샘플 조회, 지도 SDK 설정, 주소→좌표 변환 | 실제 기기 지도에 한 지역·한 달의 거래와 연결한 단지 마커 표시 |
| 1. 서버·DB 기반 | 서버 생성, DB 연결, Flyway, 공통 오류 응답, API 문서 | 서버·DB 실행 및 기본 API 호출 성공 |
| 2. 데이터 수집 | 최근 3년 거래 수집, 단지 연결, 원본·수집 이력 저장, 정정·해제 반영 | 반복 수집으로 거래가 중복되지 않고 실패 범위를 다시 수집할 수 있음 |
| 3. 지도 MVP | 지도 범위 API, 검색·필터, 가격 마커, 단지 요약 패널 | 실제 거래 데이터로 지도 탐색 가능 |
| 4. 상세·그래프 | 단지 기본정보, 면적별 거래 목록, 산점도, 건물정보 보강 | 선택한 거래의 가격·층·계약일과 데이터 출처 확인 가능 |
| 5. 단지 비교 | 후보 2~3개, 같은 조건 집계, 비교표·차이 요약 | 면적·기간 변경이 모든 비교 후보에 동일하게 적용됨 |
| 6. 로그인·관심 목록 | 실제 Google 인증, 토큰 갱신, 관심 저장·메모 | 재실행 후 계정별 관심 목록 유지, 사용자 간 접근 분리 |
| 7. 배포·안정화 | HTTPS 배포, 자동 검사, 수집 운영, 오류·성능 점검 | 설치된 앱에서 지도→상세→비교→관심 저장 전체 흐름 사용 가능 |

검증은 기능 개발과 함께 진행합니다. 특히 중복 수집, 정정·해제 반영, 지도 검색 경계, 비교 집계, 다른 사용자의 관심 목록 접근 차단을 확인합니다. 공간 검색 테스트는 PostgreSQL/PostGIS 환경에서 수행합니다.

### 바로 다음 작업

1. 첫 시·군·구를 정합니다.
2. 국토부 실거래 API와 지도 SDK 이용 설정을 준비합니다.
3. 한 달치 실제 거래를 조회하고 단지·주소 식별정보를 확인합니다.
4. 주소→좌표 변환과 SDK 57 지도·가격 마커를 Android 실제 기기에서 검증합니다.
5. 검증 결과로 데이터 구조와 API 응답 형식을 정한 뒤 서버·DB 기반을 구성합니다.

## 현재 앱 실행

Node.js 24 LTS와 Android SDK·JDK 개발 환경을 준비합니다. 다음 명령은 현재 앱 프로젝트 기준입니다.

```bash
npm ci
npm run android
```

이미 설치된 개발 앱에 개발 서버만 연결할 때:

```bash
npm start
```

타입 검사:

```bash
npm run typecheck
```

네이티브 의존성이나 네이티브 설정을 변경한 뒤에는 개발 앱을 다시 빌드합니다. 서버 실행 방법은 서버 프로젝트를 생성한 후 해당 저장소 README에 작성합니다.
